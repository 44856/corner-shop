## 0. 结论先放这里

1. **技术底子是好的。** 全部几何程序化生成、`kit.gd` 是无状态静态工具库、已有 `walk_probe` 这种真断言回归测试——这三件事恰好是很多团队想做没做成的。不要重写。
2. **瓶颈不在代码质量，在三个缺失：装配抽象、接口契约、自动验证。** 这三样正好是"一个人写"和"多人写"之间的全部差别。
3. **协作症状已经出现了，不是预测。** 任务书用「禁止改 `project.godot`」「不改 `cutscene.gd` 现有行为」来规避冲突；`grassland.gd` 头部注释承认「改名要动协作者的文件，等确认后再一起改」；README 与 `project.godot` 对"当前入口"的说法曾经不一致。这不是纪律问题，是结构问题。
4. **建议方案：加三层，不动地基。** Assembly（装配层）、Contract（契约层）、Verification（验证层）。程序化生成的约定原样保留。
5. **P0 已落地（2026-10-21）。** CI、`tools/check.sh`、CODEOWNERS、单场景运行脚本、`shots/` 出库、lfs 规则都已就位。
6. **P1 没有按原计划先做（2026-10-24 修订）。** 跨场景需求先到，实际落地顺序是：
   - **场景路由**：`GameState / WorldLinks / SceneRouter / PortalHost` 四层，目的地与禁用条件从场景脚本收进中央路由表；
   - **音频合并层**：`AudioBus / AudioVoice` + `default_bus_layout.tres`，一次性音效与命名声道统一生命周期；
   - **静态合批**：`kit.batch_static()` 把静态街景按材质合批，动态节点必须在合批之后创建。
   三项都符合 §3 的「装配一次、契约显式」原则，列入 §4.7–§4.9。`GameScene` 仍未开始；
   当前 10 组 probe、329 条断言是新的安全网。

### 1.3 已经做对的六件事（不要动）

- **程序化生成 = diff 友好。** 很多人以为"编辑器摆场景"更适合协作，实际相反：`.tscn` 里几千行 `Transform3D` 的合并冲突无法人工解决，而 GDScript 生成的几何是**文本 diff**，能 review、能 rebase。这是本工程最大的协作资产。
- **`kit.gd` 的设计。** 无状态静态函数、参数默认值克制、材质有缓存。这是整个仓库最健康的模块，应当作为其它共享库的样板。
- **`Store.layout(walkable)` 是唯一真源。** 视觉与碰撞读同一份数据，从机制上消灭了"看得见走不过去"。这个模式应当推广到所有关卡。
- **`walk_probe` 是真断言。** 14 条断言、退出码非 0 即失败。它不是"跑一遍看看"，是回归测试。
- **路由与场景解耦。** 场景只声明本地出口（触发盒、提示点、`spawn` 名），
  「通向哪、什么时候禁用、推进到哪个剧情节点」集中在 `world_links.gd`；
  `Links.resolve()` 是纯函数，`router_probe` 能不起 3D 场景直接断言 80 条路由规则。
- **音频只有一个入口。** 所有播放经 `AudioBus`：一次性音效合批复音、3D 音效走固定池、
  雨/低频用命名声道；跨场景同名申请是接管而不是叠音。生命周期随 `owner` 场景根回收。

## 2. 诊断：七个结构性问题

> 2026-10-24 复核：C / E / G 已解决；D 从 2 组扩到 10 组；F 只解决了 `interaction_hub`，
> `opening_flow` 仍读 `cutscene._ui`；A / B 仍未解决。诊断文字保留原样，作为当时的判断记录。

按**对并行开发的伤害**排序，不是按代码美观度。

### A. 装配逻辑复制，第三集必然漂移

同一件事在两个场景里各写了一遍：

| 职责 | `store_walk.gd` | `grassland.gd` |
|---|---|---|
| 造玩家 | `_setup_player()` L81 | `_setup_player()` L363 |
| 造 HUD | `_setup_hud()` L163 | `_setup_hud()` L467 |
| 注册交互 | `_setup_interactions()` L170 | `_setup_interaction()` L491 |

`_setup_hud` 的两份实现里，`controls` 数组、`add_child`、`fade_in` 的顺序几乎逐字相同，只有文案配色不同。`_setup_player` 则是同构不同参（夜景要压暗、要锁输入、要初始朝向）。

**后果**：加第三集就要复制第三遍。某天有人调了玩家镜头手感，只改了一集，另外两集的手感就开始分叉，而且没有任何测试会发现——因为 probe 只测"能不能走过去"，不测手感。

**根因**：没有"关卡"这个抽象层。场景脚本同时承担了「框架装配」和「本关编排」两种职责。

**2026-10-24 复核**：仍未解决。`gas_station.gd` 已经到 1567 行，说明装配复制的成本还在增长；
但路由层把「跨场景目的地」从装配里拿了出去，至少第三集不需要再抄一份出口逻辑。

### B. 共享造型库没有契约，改签名是隐形破坏

`Store.build(root, opts)` 被 `main.gd`、`store_walk.gd`、`backup/diorama_orbit.gd` 三处调用，而 `walkable` 选项只有 `store_walk` 传 `true`。也就是说：`store.gd` 里任何一次布局修改，必须同时满足三种语义（展示版不能变、可玩版要能走、备份版要冻结）。

`Store.layout(walkable)` 同时被 `_interior()` 和 `collision_layout.gd` 读取——**一个人改布局，视觉和碰撞两边同时动**。这是设计上的正确，但没有任何东西阻止别人只改其中一边的假设。

**后果**：改 `store.gd` 的人需要知道全部 3 个调用方的前提。这个知识现在只存在于上一个改它的人的脑子里。

### C.「禁止修改」替代了所有权

这是最值得说的一条。

- 任务书 01：**不改** `scripts/cutscene.gd` / `scripts/main.gd` 的现有行为；**不改** `project.godot`。
- 任务书 02 同样以此为前提设计了 `walkable` 开关和 `diorama_orbit` 冻结副本。
- `grassland.gd` 头部注释：*"文件名仍叫 grassland 是因为 scenes/grassland.tscn 与 opening_flow 都引用了它，**改名要动协作者的文件，等确认后再一起改**。"*

冻结 `project.godot` 的直接代价，可以在代码里逐条数出来：

1. 不能加 autoload → 对话状态机退化成「由场景实例化的普通节点」，`dialogue_runner.gd` 自己在注释里写明了这个妥协。
2. 不能写 `[input]` 段 → 输入必须在代码里注册，于是出现了**三份**注册逻辑：`player_controller._ensure_actions()`、`interaction_hub._ensure_action()`、`dog._ensure_action()`。
3. 三份注册已经漂移：`dog.gd` 的 `prompt_text` 是「按 F 说话」，而 `interaction_hub` 注册的是 `E` 并额外"补上 E"。同一个交互，两套键位记忆。

**结论**：「禁止改某个文件」不是协作规范，是协作失败的补救措施。它把一个本该由 review 承担的风险，转成了全项目长期的技术债。

### D. 没有自动化验证，并行开发没有安全网

`walk_probe` / `grassland_probe` 存在且有效，但：

- 要人记得手动跑；
- 没有 CI，合并前没人能证明自己没弄坏别人的场景；
- 引擎二进制不入库、`.godot/` 不入库（这个是对的），新成员第一步是"找引擎 + 导入 42MB 资源"，README 里专门写了一节提醒——这本身就是摩擦。

**后果**：A 改了 `store.gd`，B 在自己分支上是绿的，合并进 `develop` 之后才发现门走不进去了。等发现时，已经又叠了三个提交。

### E. 入口与构建不可重现

- `project.godot` 的 `run/main_scene` = `res://scenes/opening_flow.tscn`
- README 的表格写「**可玩版**（当前入口）`scenes/store_walk.tscn`」

**新成员按 F5，看到的和文档描述的不是同一个东西。** 这类不一致在单人开发时只是小瑕疵，在多人协作时是"我的环境和你不一样"的第一块多米诺骨牌。

### F. 私有字段成为跨模块接口

- `walk_probe.gd` 直接读 `world.door`、`world.hub`、`hub._focus`（下划线私有）。
- `opening_flow.gd` 靠 `c.get_script() == CUTSCENE_SCRIPT` 认节点，再读 `cutscene._ui`。

这不只是"不优雅"。它意味着任何内部重构（改个字段名、把 `_focus` 抽出成 `focused_target()`）都会**静默打断**外部依赖，而打断的一方不会收到任何编译错误——GDScript 的 `get()` 与动态调用都是运行时的。

### G. 产物混进仓库

`shots/` 21 MB 截图入库。每次按 README 的 `-- --shot` 重渲，就会产生一批二进制 diff：review 时看不出来、clone 时全量下载、历史永久膨胀。`assets/` 42 MB 的 `.glb` 同理。

## 3. 目标架构

### 3.1 三条设计原则

| 原则 | 含义 | 解决的问题 |
|---|---|---|
| **编排与造型分离** | 关卡只决定「放什么、放哪、什么参数」，造型库决定「长什么样」 | 已有，继续强化 |
| **装配一次，关卡只声明** | 玩家/HUD/交互中枢/音频由框架装配，关卡填一张声明表 | 诊断 A |
| **契约显式，验证自动** | 共享库的公开签名视为契约；契约由 CI 验证 | 诊断 B、D |

### 3.2 分层

```
┌──────────────────────────────────────────────┐
│ content/   关卡编排：每集一个目录              │  只声明，不实现
│            store_walk / grassland / opening   │
├──────────────────────────────────────────────┤
│ systems/   横切系统                            │
│            dialogue / hud / interaction /      │
│            audio / camera                     │
├──────────────────────────────────────────────┤
│ actors/    角色                                │
│            player_controller / actor /         │
│            npc_base / dog / npc_guard          │
├──────────────────────────────────────────────┤
│ world/     造型库（有契约、有 owner）           │
│            kit / materials / street / store /  │
│            props / terrain / city_wall         │
├──────────────────────────────────────────────┤
│ core/      框架（部分已落地）                   │
│            scene_router / portal_host /        │
│            world_links / game_state /          │
│            game_scene(未做) / input_actions(未做)│
└──────────────────────────────────────────────┘
```

**依赖规则**：只能向下依赖，**禁止同层横向复制**。`systems/hud` 可以被 `content` 用，`content` 不可以被 `systems` 反向引用。`world` 层不允许出现 `get_node("../Player")` 这类跨层查找——它只接受 `parent: Node3D` 参数并往上面挂东西，这是 `kit.gd` 已经做对的地方。

> **现状**：实际目录只有 `scripts/core/`（`game_state / world_links / scene_router / portal_host`）
> 与 `scripts/audio/`（`audio_bus / audio_voice`）两个子目录，其余模块仍在 `scripts/` 根。
> 上面的分层图是目标；§3.3 的目录是迁移目标，不是现状路径。不要按图去找 `core/game_scene.gd`。

## 4. 关键设计

### 4.1 `GameScene`：消灭装配复制

> **状态（2026-10-24）：未实现。** 下面保留为目标设计。当前 `store_walk.gd` 已到 597 行，
> 装配复制的问题仍然存在；先落地的是更急的路由与音频（§4.7–§4.8）。

目标：关卡脚本从 394 行（`store_walk.gd`）降到 60–80 行，且第三集不需要再抄一遍。

```gdscript
# core/game_scene.gd
class_name GameScene
extends Node3D
## 关卡基类：负责「怎么装」，子类只回答「装什么」。
##
## 约定：子类实现 _describe()，不要覆写 _ready()。
## 需要额外初始化时覆写 _on_assembled()。

var player: CharacterBody3D
var hud: CanvasLayer
var hub: Node
var env: Environment

func _ready() -> void:
    var d := _describe()
    _assemble_world(d)
    _assemble_player(d)
    _assemble_ui(d)
    _assemble_interactions(d)
    _on_assembled(d)

## 子类唯一必需的实现。返回本关的声明表。
func _describe() -> Dictionary:
    push_error("GameScene: 子类必须实现 _describe()")
    return {}

## 装配完成后的钩子：开场演出、镜头推近、剧情触发。
func _on_assembled(_d: Dictionary) -> void:
    pass

## 公开 API：注册一个交互点（替代直接操作 hub 内部）
func add_interaction(pos: Vector3, radius: float, text: String, cb: Callable) -> void:
    hub.add_target(pos, radius, text, cb)

## 公开 API：当前聚焦的交互点文案（给测试用，不要再读 hub._focus）
func focused_prompt() -> String:
    return hub.focused_text()
```

子类长这样：

```gdscript
# content/store_walk/level.gd
extends GameScene

const SPAWN := Vector3(0.35, 0.17, 0.95)

func _describe() -> Dictionary:
    return {
        "world": {"street": true, "store": {"walkable": true}, "props": true},
        "player": {
            "spawn": SPAWN,
            "face": PI,
            "tint": Color(0.52, 0.55, 0.66),   # 夜景压暗
            "shade_floor": 0.34,
            "camera": {"dist": 3.9, "height": 1.52, "fov": 52.0, "shoulder": 0.10},
        },
        "hud": {
            "title": "HOSHI MART", "zone": "店外 · 人行道",
            "accent": Color("#4dffa8"),
        },
        "interactions": [
            {"pos": Vector3(1.35, 1.0, -4.55), "r": 1.75, "text": "拉开冷柜", "cb": _on_fridge},
            {"pos": Vector3(0.0, 1.0, -3.85),  "r": 1.55, "text": "翻一翻货架", "cb": _on_rack},
            {"pos": Vector3(2.58, 1.0, -3.0),  "r": 1.35, "text": "按服务铃", "cb": _on_bell},
            {"pos": Vector3(0.98, 0.4, -0.52), "r": 1.30, "text": "摸摸猫", "cb": _on_cat},
        ],
    }
```

**为什么用 Dictionary 而不是 `@export` 字段**：`@export` 要在编辑器里填，而这个工程没有可摆的场景；Dictionary 让声明集中在一屏内，diff 是一块连续文本，review 时能一眼看完"这一关改了什么"。

**注意**：这是**声明表**，不是配置文件。类型检查靠 `_assemble_*` 里的 `as` 转换与默认值兜底。不要把几百行逻辑塞进 `_describe()`。

### 4.2 契约：共享库的公开面

> **状态（2026-10-24）：部分落地。** `docs/contracts/` 仍未建；路由与音频的契约先写进了
> [`场景路由.md`](场景路由.md) 与 [`音频总线.md`](音频总线.md)。`store / kit / props / street`
> 的契约页仍待补。

新增 `docs/contracts/<模块>.md`，每个共享库一页，只写三样东西：

1. **公开 API**（签名 + 语义，不是实现说明）
2. **不变量**（调用方可以依赖的前提）
3. **禁止事项**（明确写清"不要从外部改 X"）

以 `store.gd` 为例：

```markdown
# store.gd 契约

## 公开 API
- `build(root: Node3D, opts: Dictionary = {}) -> void`
  - `opts.walkable: bool = false` — true 时按可行走布局建造（货架留 0.83m 过道）
- `layout(walkable: bool) -> Dictionary` — 布局数据的唯一真源

## 不变量
- `build()` 与 `collision_layout.gd` 必须读同一份 `layout()` 结果
- `walkable = false` 时的几何不得因 `walkable = true` 的新增字段而改变
- 门洞范围固定为 x ∈ [-0.33, 1.04]

## 禁止
- 外部代码不得直接修改 `layout()` 返回的字典（它是共享引用）
- 新增 `opts` 键必须默认为旧行为，否则是破坏性变更
```

**破坏性变更的规矩**：改共享库的公开签名，必须在**同一个 PR** 里更新全部调用方，并在 PR 描述里贴出 `grep` 结果。旧签名需要保留一期时，用内部转调：

```gdscript
static func build(root: Node3D, opts: Dictionary = {}) -> void:
    _build_impl(root, opts)
```

| 层 | 内容 | 当前实现 |
|---|---|---|
| 1. 解析 | 所有 `.gd` 语法 / 类型检查 | `check.sh` 在 `.gd` 哈希变化时跑 `--headless --editor --quit`；`lint_rules.sh` 的 R4 顺带查断链 |

`.github/workflows/ci.yml`：

实际文件：`.github/workflows/ci.yml`。它做四件事：

1. 缓存并安装 Godot 4.7.2 到 `~/godot/godot`（`tools/_godot.sh` 最后一条探测规则正好命中，CI 不需要额外传 `GODOT_BIN`）；
2. 缓存 `.godot/`，key 带上 `assets/` `shaders/` `audio/` `project.godot` 的哈希；
3. 跑 `./tools/lint_rules.sh`（几秒，坏了不必等 probe）；

**CI 不重复实现判定逻辑**，这是刻意的：probe 的发现、执行、失败判定全在 `check.sh` 里，
本地和 CI 走同一条路径，才不会出现"本地绿、CI 红"。如果要改判定标准，改脚本一处即可。

**probe 的写法要求**（现有 probe 已符合，固化成规范）：

- 每条断言打印 `[ OK ]` / `[FAIL]` 与实测值，不要只打 `assert`；
- 失败时 `get_tree().quit(1)`，让 CI 能判；
- 只断言**对外可观测**的状态：世界坐标、`hub.focused_text()`、`door.is_open()`。**不准读 `_` 开头的字段**——`walk_probe` 里的 `hub._focus` 已在 P0 修掉，`world.door` / `world.hub` 这类场景公开字段是允许的。

### 4.7 场景路由：出口本地化，目的地集中化（2026-10-23 落地）

四层，依赖单向：

```
GameState（剧情节点 + flag，纯数据）
    ↑
WorldLinks（SCENES + ROUTES，纯数据 + static resolve）
    ↑
SceneRouter（autoload：查路由 / 转场生命周期 / 到达上下文）
    ↑
PortalHost（场景内出口：walk 触发盒 + E 交互点）
```

- `PortalHost` 知道门在哪，不知道门通向哪；
- `WorldLinks` 知道通向哪，不知道门长什么样；
- `SceneRouter` 只做四件事：查路由、锁旧场景、播转场、把「从哪来、落在哪个 spawn」交给新场景；
- 场景在 `_ready()` 最前面 `bind_scene()` + `consume_arrival()`，用 arrival 决定落点、朝向、
  镜头 yaw 和是否播苏醒独白。

关键规则：

- 路由键查找：精确剧情节点 → `*` 通配 → `default`，覆盖项与 `default` 浅合并；
- **反向出口不写 `set_story_node`**，否则从加油站回来会把剧情倒回第二幕；
- 未知场景 / 未知剧情节点当场失败；失败的 `goto` 不留任何状态变更；
- 同一时间只允许一个转场层（`root` 下已有 `LetterTransition` 时拒绝第二次切换）。

完整的数据结构、接入步骤和常见坑见 [`场景路由.md`](场景路由.md)。

### 4.8 音频：一个入口，四种形态（2026-10-23 落地）

`AudioBus` 是 autoload，所有声音都从它走：

| 接口 | 形态 | 用途 |
|---|---|---|
| `play_2d` | 每条总线一个 16 复音播放器 | 门铃 / 服务铃 / 广播等一次性 2D |
| `play_3d` | 12 个播放器的固定池 | 世界里的短音效 |
| `play_on` | 每个 3D 节点一个 8 复音播放器 | 连续触发、需要跟着节点走 |
| `channel` | 命名专用播放器，可循环 / 淡变 / 跟随 | 雨、低频、耳鸣、剧情声道 |

`AudioVoice` 是返回句柄，屏蔽「专用播放器」与「复音流 id」两种形态。
三条总线（Ambience / SFX / Music）在 `default_bus_layout.tres` 里，Master 挂 HardLimiter。

跨场景约定：

- **声道名是接口**：`rain` / `hum` 在三个可玩场景复用，同名申请是接管而不是叠音；
- 循环设在流的副本上，不能改 `Sfx.*` 的静态缓存；
- 长音必须传 `owner`（场景根），场景卸载时自动淡出；autoload 不持有节点引用；
- 一次性音效按场景 scope 自动回收，循环声道必须走 `stop_channel()`；
- **转场切声**：`SceneRouter.goto()` 进转场时调 `AudioBus.cut_for_transition()`，
  旧场景的声道 / 一次性音效 / 3D 池一起收，切场景之前保持静音；新场景的
  `_setup_audio()` 在切场景之后才申请。

完整接口与示例见 [`音频总线.md`](音频总线.md)。

### 4.9 静态合批的边界（2026-10-23 落地）

`kit.batch_static(root, branches)` 把静态子树里的 `MeshInstance3D` 按「材质 + 阴影设置」
合并成 `SurfaceTool` 网格。商店街 2500+ 个 MeshInstance 可收成几百批。

规则：

- **必须在静态几何建完之后、玩家 / 门 / 碰撞等动态节点创建之前调用**；
- 只合并使用 `toon` ShaderMaterial、无子节点、无脚本、非蒙皮的三角形 `MeshInstance3D`；
- 带脚本或 `CollisionObject3D` 的子树整体跳过，所以自动门、角色、交互物不会被误烘；
- 新增「会动的建筑件」（旋转招牌、可开门叶）不要放进合批分支，或让它带脚本 / 碰撞体。

当前调用点：`store_walk`、`hoshi_street`、`gas_station`。

## 5. 协作流程

### 5.1 分支模型：trunk-based，不是 git-flow

```
main       ← 可发布快照（当前无导出配置，暂与 develop 同步）
develop    ← 主干，永远绿
feature/<集号>-<模块>   ← 寿命 ≤ 3 天，例如 feature/ep3-market-street
backup/<名字>           ← 冻结标签/分支，只读
```

规则：

- **禁止**长期 `feature` 分支。超过 3 天未合并的，必须拆小或先合入未完成的空实现。
- **禁止**直接在 `develop` 上提交。所有改动走 PR，哪怕 2 人。
- `backup/*` 分支不可写，只用来对照与回滚。

### 5.6 给 AI 的规则文件

`README.md` 教「怎么跑」，本文教「为什么这么分层」。AI 需要的是第三样东西：
**不许怎么做**，以及**这个工程哪里反直觉**。前者它读得懂但不会主动遵守，后者它按常识
一定会推错（例如「躺下就转 −80°」——错，这个模型的枢轴在脚底，−90° 才对）。

三份文件的关系：

| 文件 | 角色 |
| --- | --- |
| `AGENTS.md` | **唯一真源**。铁律 R1–R9、反直觉清单、命令、风格 |
| `CLAUDE.md` | 薄指针 + 三件最易忘的事 + 两条最易踩的坑 |
| `.github/copilot-instructions.md` | 薄指针 + 五条摘要 |

**不复制正文。** 复制就会漂移，而漂移的规范比没有规范更糟——它会让 AI 读到两份互相矛盾的
指令，然后随机挑一份执行。

规则分两类，这个区分比规则本身重要：

- **可自动检查（R1–R6）** → `tools/lint_rules.sh`，进 CI，几秒出结果。
  场景有没有被摆节点、probe 有没有读私有字段、输入注册有没有新增第四份、`res://` 有没有断链、
  默认入口是否存在、产物有没有混进索引。
- **不可自动检查（R7–R9）** → 只能靠 review。跑回归、契约意识、不引框架。

写规则的三条原则，来自这次的实践：

1. **每条给「为什么」。** 只给禁令，AI 会在没覆盖到的地方自己发挥；给了理由，它能泛化。
   「不许摆节点」不如「摆节点会产生无法人工合并的 Transform3D 冲突」。
2. **只写反直觉的。** Godot 常识不用写，写了是噪声，会稀释真正的警告。
3. **能检查的不要只写在文档里。** 文档是给人看的，退出码是给流程用的。
   「禁止提交截图」写在文档里三天就失效，写成 R6 就永远有效。

- **引擎探测**：`tools/_godot.sh` 按 `GODOT_BIN` → 项目根 → `~/godot*/Godot_v*-stable_linux.x86_64` → `~/godot/godot` → `PATH` 顺序找引擎。当前这台机器命中 `/home/alice/godot-spike/`。

  CI 缓存的 `.godot` 里 `global_script_class_cache.cfg` 可能是旧的，新增 `class_name` 会报
  「Could not find type」，而且本地永远复现不了。详见 §4.5。

## 7.5 单场景运行（不改主文件）

这是 P0 附带的工具，值得单独说明，因为它改变的是**日常习惯**而不是代码。

过去要单独看一个场景，得改 `project.godot` 的 `main_scene`，或者改 `opening_flow.gd` 的
`NEXT_SCENE`——改完忘了改回来，就成了"我这边怎么和文档不一样"。

现在的入口只有一条：

```bash
./tools/run.sh <场景名>
```

| 命令 | 作用 |
|---|---|
| `./tools/run.sh` | 默认入口（`project.godot` 的 `main_scene`） |
| `./tools/run.sh store_walk` | 简写 → `res://scenes/store_walk.tscn` |
| `./tools/run.sh walk_probe` | probe（`tools/` 也在搜索路径里） |
| `./tools/run.sh list` | 列出所有可跑场景 |
| `./tools/run.sh --editor store_walk` | 编辑器打开该场景 |
| `./tools/run.sh --headless walk_probe` | 无窗口 |
| `./tools/run.sh store_walk -- --shot` | `--` 之后原样传给场景 |
| `./tools/run.sh -n store_wal` | dry run，只打印命令 |

两个刻意的设计：

1. **唯一前缀匹配，歧义就拒绝。** `store_wal` 能命中 `store_walk`；`g` 会同时命中
   `grassland` / `grassland_probe` / `guard_shot`，此时脚本报错并列出候选，**不会猜**。
   场景名猜错的代价是"跑了五分钟才发现跑的是另一个场景"，不如直接失败。
2. **`-n` 必须存在。** 没有 dry run，就没法验证脚本自己的解析逻辑——这个选项是写脚本时
   用来测脚本的，后来发现日常也好用（确认 `--shot` 有没有被吞掉）。

## 8. 明确不做

- **不引入 ECS。** 这个项目是"手搓场景"，实体数量在几十个量级，ECS 的抽象成本远大于收益。
- **不把程序化生成改成编辑器摆场景。** 会直接失去本工程最大的协作优势：文本 diff。
- **不做"为将来 20 人准备"的过度设计。** 现在 2 人，合理目标是 5 人以内。所有规范都应能在 5 人规模下被自觉执行，否则就是纸面制度。
- **不删 `backup/diorama_orbit.gd`。** 它是编排的冻结副本，价值在于"随时随地能跑一遍旧版对照"，不是死代码。
- **不给每个脚本加 `class_name`。** 现在用 `preload` 常量已经清晰；`class_name` 会引入全局命名空间，与 `GameScene` 这类基类冲突的风险大于收益（`DialogueRunner` 已经是特例，保留即可）。
